## Feature idea (verbatim from the course, Ukrainian)
Додаткові завдання (Stretch, без дедлайну):

1. **Евал власного скіла в evals/.** Проблема: скіл, який ви написали в L02, досі живе без регресійного захисту: будь-яка правка description чи інструкцій може тихо зламати його поведінку, і ви дізнаєтесь про це через тиждень з дивного рев'ю. Що зробити: додати в пакет evals/ файл skills/<ваш-скіл>/<ваш-скіл>.eval.ts з 3–4 кейсами за зразком з лабораторної: підібрати фікстуру (фрагмент коду чи сценарій, на якому скіл має проявити себе); написати кейс через skillTask + практики для судді (а якщо очікування — конкретні факти, спершу patternMatch); прогнати, подивитись вердикт з цитатами-доказами, відкалібрувати практики; зламати скіл навмисно → тест червоний → відкат → зелений. Ключова ідея: той самий механізм, що на лабораторній, але на власному артефакті.

2. **Case Editor — ручне створення кейсів.** Проблема: кнопка «→ eval case» покриває лише те, що агент уже колись знаходив або флажив. Кейси для багів, яких агент ще не бачив (чужий інцидент, edge case з код-рев'ю колеги), створити нізвідки. Що зробити: форма створення і редагування кейса вручну: вставити diff-фрагмент (з DiffView-прев'ю), задати тип очікування, файл і діапазон рядків. Створені вручну кейси живуть у тому ж наборі і проганяються тим самим роутом. Ключова ідея: датасет росте з двох джерел — з історії рішень і з передбачення майбутніх провалів.

3. **Тренд-графіки метрик.** Проблема: порівняння двох прогонів показує стрибок, але не динаміку; чи деградує precision повільно від версії до версії, видно тільки на графіку. Що зробити: графік recall / precision / citation_accuracy по всіх прогонах агента на вкладці Evals; точка = прогін, тултіп = версія промпта і вартість. Ключова ідея: «CI-як-тренд» — спершу дивимося динаміку, пороги вводимо потім.

4. **PreToolUse hook — детермінований гейт у harness.** Проблема: евал — ймовірнісна перевірка з порогом, а деякі правила мають виконуватися завжди, напр. «не комітити без зелених тестів». Що зробити: один PreToolUse-hook у .claude/settings.json — тест-гейт перед комітом. Два готові приклади лежать у template (прочитати, свій написати за зразком). Попрацювати кілька сесій і задокументувати один реально зловлений випадок — що агент намагався зробити і що його зупинило. Ключова ідея: ймовірнісне міряємо евалами, критичне блокуємо hook'ом.

5. **Mutation testing на одному файлі.** Проблема: зелені тести кажуть «поточний код проходить», але мовчать про якість самих тестів. Що зробити: за бонус-матеріалом уроку прогнати мутаційний інструмент на одному модулі DevDigest, подивитись скільки мутантів вижило; по одному вцілілому мутанту дописати тест, який його вбиває. Ключова ідея: евал для ваших тестів — «перевіряй перевіряльника» на рівень нижче.
