- **(b) Skill-owned cases and runs (UF):**
  - Case creation from a finding: `GET /findings/:id/eval-skills` returns `EvalSkillOffer[]` `{skill_id, skill_name, has_case}`, listing only skills in the run's `run_skills`. `POST /findings/:id/skill-eval-case` takes `{skill_id: uuid}` and returns 201 or 200 if the case exists.
  - Run routes: `GET /skills/:id/eval/carriers`, `GET /skills/:id/eval/estimate?carrier_agent_id=`, `POST /skills/:id/eval/runs` (body `{carrier_agent_id: uuid}`, replies 202 `{run_id, status, estimate}`, rate limit 5/min), `GET /skills/:id/eval/runs`, `POST /eval/skills/runs/all` (body `{confirm: true}`), `GET /eval/skills/compare?a=&b=`. The dashboard `GET /eval/dashboard` now also returns `skills: EvalSkillSummary[]` `{skill_id, skill_name, cases_total, carrier_agent_name, latest, tokens_per_run}`.
  - Run refusals (`startSkillRun`): 404 for a missing skill or carrier. 409 `run_in_flight`. 422 `no_cases`, `no_agent_linked`, `provider_not_configured`. Stale `running` runs older than 15 min are reconciled to errored first.
  - **How a skill is executed:** a skill cannot run alone, so it runs inside a chosen "carrier" agent that must be linked to it. Each case is run twice through the same review engine (`EvalExecutor.runCase` → `reviewPullRequest`). The two arms differ only in the skill block, built by `buildArms` in `executor.ts`. The with-arm bypasses both enable gates and sets `gates_bypassed`. The task line is the constant `EVAL_TASK_LINE` plus the case's frozen PR title. Only the case's frozen diff and PR body go in; there is no repo map, callers digest or project context. It writes no `agent_runs` or `run_skills` rows.
  - **What is scored (deterministic, no LLM judge, `scoring.ts`):** a finding matches when the file is equal and the line ranges intersect. `must_find` passes with at least 1 match. `must_not_flag` passes with 0 matches. Recall is passing must_find over must_find cases. Precision is `1 - FP/total_kept_findings`. Citation accuracy is `grounding_kept/grounding_total`. Each is null when its denominator is 0.
  - Metrics are computed per arm with `scoreRun`. The with-arm values go in the normal run columns, and the whole without-arm `EvalRun` goes in `arm_without`.
  - `lift = with − without` per metric, null if either side is null. `classifyEffects` gives each case one of `helped|hurt|no_effect_pass|no_effect_fail`. A case that errors in either arm is excluded from both arms (`pairArms`, reason "paired arm failed").
  - Run record: `EvalSkillRunRecord = EvalRunRecord + {skill_version, carrier_agent_id, carrier_agent_name, gates_bypassed, arm_without, lift, effects, effect_counts}`. Estimate: `executions_total = 2 × cases`.
  - **Trend and metrics per skill:** the dashboard keeps no trend series for skills, only `latest` plus `tokens_per_run`. Agents get `EvalTrendPoint[]`. For skills the client reads `GET /skills/:id/eval/runs` (the full run list). `skillCompare` recomputes each run's lift over the common case set and also returns `carrier_differs` and `skill_body_diff` (`diffLines` of the two `skill_versions` bodies). Metric tiles show lift next to token cost. I did not read `SkillMetricTiles.tsx` or `SkillRunHistory.tsx` closely, so how the UI renders trends is unconfirmed.
