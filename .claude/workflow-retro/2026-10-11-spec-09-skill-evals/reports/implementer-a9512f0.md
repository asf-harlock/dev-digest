### Behaviour implemented
- **NFR-5:** `owner_kind='agent'` is now on `agentRuns` (covers `listRunSummaries`, `countFinishedRuns`, `latestFinishedRunRow`), `runningRunId`, `recentRunSummaries` (dashboard), `deleteByAgent`, and `compare` (a skill run id gives 404, EC-38). `caseCountsByAgent` already filtered cases by owner.
- **Start (`startSkillRun`):**
  - Check order: 404 skill, 404 carrier, 422 `no_agent_linked` (no agent linked, or the carrier is not linked), 422 `no_eval_cases`, insert, 409 `eval_run_in_progress` with `details.run_id` from the per-skill partial unique.
  - Snapshots the skill and carrier, builds both arms (AC-24 tie rule: the skill under test goes after every other skill with the same order, regardless of both enable flags), reads cases once, returns 202 before any review, runs detached.
- **Execute (`executeSkillRun`):**
  - Per case, with-arm then without-arm, both through `reviewCase`/`reviewFrozenCase`, so prompt parity holds by construction. `isRunning` is checked before EACH review, so a deleted skill stops with no further LLM call, no write and only an info log (EC-24).
  - Progress is saved per case (both arms).
  - Finalize: `pairArms`, then `scoreRun` per arm, `computeLift`, `finalStatus`. All errored gives status `errored` with null metrics and lifts and the first error reason (EC-17).
  - Cost is null if either arm of any scored case is null.
  - A crash finalizes the run as errored without wiping saved progress.
- **Reads:**
  - `skillOverview` returns carriers (with `link_enabled`), `latest`, `previous` (2 newest finished runs) and `trend` (up to 100, chronological). The trend reads scalar columns plus the small `lift` jsonb only (NFR-13).
  - `listSkillCases` and `getCase` derive `latest_result` from the newest finished skill run. The list item uses with and without states, effect, with-arm counts and cost summed over both arms (AC-40). The detail uses the with-arm state and counts with duration and cost summed over both arms (AC-59).
- **NFR-12:** logs carry only run id, skill id, skill version, carrier id, case count, status and duration.

### Decisions where the plan was silent
1. `skill_name` on `EvalSkillRunRecord` in the overview (`latest`/`previous`) is the skill's live name, because the snapshot jsonb is not read there (NFR-13). The run detail uses the snapshotted name.
2. `pairArms` differs slightly from upstream: when one arm errored, BOTH arms store the failing arm's real error reason (not "paired arm failed"), so AC-40's `error_reason` is useful. "paired arm failed" is only the fallback.
3. The without-arm tie order for skills with equal link `order` is by skill name, then id, for determinism. The live path has no defined tie order.
4. `EvalRunSummary` and the skill summaries use `sql<string>` casts on the nullable `agent_id`, `skill_id` etc. in selections that always filter by `owner_kind`; this states the invariant in types. The full-row helpers are `isAgentRunRow` and `isSkillRunRow`.
5. The error messages for `no_eval_cases` and `eval_run_in_progress` were made owner-neutral ("There are no eval cases to run." / "An eval run is already in progress."). No test asserted the old text.
6. Pure arm logic is in `arms.ts`, not `scoring.ts` (the NFR-1 import-purity test).
